# CaliForge — Codex Dev Notes

Lessons learned, bugs hit, and fixes applied. Read this before every session.

---

## Architecture

- **Monorepo**: pnpm workspaces — `apps/web` (Next.js 14), `packages/db` (Prisma), `packages/trpc`  
- **Auth**: NextAuth v5 (`auth.ts` at root of `apps/web`)  
- **ORM**: Prisma 5.22 with PostgreSQL (Neon in production)  
- **Realtime**: Pusher (optional — app works without it)  
- **Billing**: Stripe Checkout Sessions (server-side redirects, no client Stripe.js)  
- **Deploy**: Vercel serverless (pnpm monorepo)  
- **Theme**: dark by default; user can toggle via `ThemeProvider` (`next-themes`)

## Critical Lessons — Do Not Repeat These

### 1. Prisma RHEL Engine Missing on Vercel (FIXED)

**The Problem**: Next.js uses a tool called "File Tracer" to decide which files from your project need to be included in the final serverless function bundle. Because Prisma loads its query engine binaries dynamically at runtime (using a path that varies by OS), Next.js's static analysis fails to "see" that these binaries are required. This results in a `PrismaClientInitializationError` on Vercel because the engine file (`libquery_engine-rhel-openssl-3.0.x.so.node`) is missing from the deployment.

**The Fix**: We use a post-build script (`scripts/copy-prisma-engine.mjs`) that scans all `.nft.json` manifest files generated by Next.js and manually injects the path to the Prisma binary. This ensures Vercel includes the engine in the bundle.

**Key Requirement**: In a monorepo setup, you must set `outputFileTracingRoot` inside the `experimental` block of your `next.config.mjs`. This tells Next.js to trace dependencies from the root of the monorepo rather than just the application folder.

```javascript
// apps/web/next.config.mjs
experimental: {
  outputFileTracingRoot: path.join(__dirname, '../../'),
},
```

### 2. Pusher Client Crash When Key is Missing

**The Problem**: When the Pusher client is instantiated at the top level of a file (e.g., `new PusherJs(process.env.NEXT_PUBLIC_PUSHER_KEY, ...)`), the code executes as soon as the module is imported. If the environment variable is missing (common in local development or PR previews), the Pusher library throws an immediate error: `"You must pass your app key when you instantiate Pusher"`. This can crash the entire page or build.

**The Fix**: Implement a `getPusherClient()` utility that checks for the key before instantiating. If the key is absent, it returns `null` and logs a warning instead of throwing. All calling components (like `useAlertBadge` or `DiscoveryProgress`) must check if the client is `null` before attempting to use it.

### 3. React Controlled Form State Sync

**The Problem**: React manages form inputs using its own internal state (`useState`). If you attempt to automate form filling by setting the DOM element's `.value` property directly (e.g., `document.querySelector('input').value = 'test'`), React's internal state does not update because it relies on "Synthetic Events" (like `onChange`). Submitting the form after a direct DOM edit will often send the *old* state or empty values.

**The Fix**: When automating or testing, you must simulate real user interactions. Use a reference to the element and then perform a "click" and "type" action. This ensures that React's event listeners are triggered and the state stays in sync with the UI.

---

### 4. Vercel Logs Resolution Lag

**The Problem**: When you run `vercel logs <domain>`, the CLI resolves the domain to the deployment currently receiving traffic. If you have just pushed a new deployment, there is often a short window where the domain still points to the *previous* deployment. If that previous deployment was failing, you might see old error logs and think your fix didn't work.

**The Fix**: Always use the specific deployment URL or ID (e.g., `califorge-abc123xyz.vercel.app`) when checking logs immediately after a deploy. This guarantees you are seeing the logs for the code you just pushed.

---

### 5. Stripe Price IDs Consistency

**The Problem**: Stripe Price IDs (like `price_123...`) are environment-specific. If you hardcode an ID from your test account into production (or vice versa), checkout sessions will fail. Furthermore, if you haven't created the products and prices in your Stripe dashboard yet, the environment variables will be empty, leading to "Price not found" errors.

**The Fix**: Use the `scripts/setup-stripe.mjs` utility. This script uses your `STRIPE_SECRET_KEY` to programmatically create all required products (Starter, Pro, Credit Packs) in Stripe, fetches their IDs, and automatically patches your local `.env` file. This ensures your environment variables always match the actual data in your Stripe account.

---

### 6. Stripe Webhook Secret (The "Chicken-and-Egg" Problem)

**The Problem**: You cannot generate a `STRIPE_WEBHOOK_SECRET` until you have a live URL to tell Stripe where to send events (e.g., `https://califorge.com/api/webhooks/stripe`). However, your code needs this secret to verify that incoming webhook requests are legitimate.

**The Fix**: This must be a manual step after the first deployment.
1. Deploy the site to get your Vercel URL.
2. Go to the Stripe Dashboard (or use `stripe listen`) and register the URL.
3. Copy the generated "Signing Secret" (`whsec_...`).
4. Add it to Vercel using `vercel env add STRIPE_WEBHOOK_SECRET production`.
5. Re-deploy or redeploy-env to make the secret available to your app.

## Astro & Clerk Lessons — Project Specific

### 7. Astro Catch-all Routing for Clerk
**The Problem**: When setting up Clerk's organization or user profile components in Astro, using Next.js-style optional catch-all routes (e.g., `[[...index]].astro`) causes "Invalid route" errors or 404s. Astro's routing engine expects single brackets for catch-all parameters.

**The Fix**: Use `[...index].astro` or `[...slug].astro` for any routes that wrap Clerk components like `<UserProfile />` or `<OrganizationProfile />`. This ensures Clerk can handle its internal sub-navigation (like `/user-profile/security`) correctly.

### 8. Public Assets in Automated Emails
**The Problem**: If you reference images using local paths (e.g., `/public/logo.svg` or `./logo.png`) in email templates (like `register.ts`), the images will appear broken to the end user. Email clients cannot access your local server or relative file paths.

**The Fix**: All images and assets in email templates must use **absolute URLs** hosted on a public CDN or your production domain (e.g., `https://dosales.com/logo.png`). During development, you can use a service like `ngrok` or host temporary assets to test visibility.

### 9. Clerk Component Hydration in Astro
**The Problem**: Clerk components like `<SignIn />` or `<UserButton />` are interactive React components. If included in an Astro page without a hydration directive, they may render statically or not function at all (e.g., buttons won't click).

**The Fix**: Always use the `client:load` or `client:visible` directive when using Clerk components in `.astro` files to ensure the React island is hydrated correctly.
```astro
<UserButton client:load />
```
